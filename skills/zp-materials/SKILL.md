# 职业资产系统构建

<!-- companion-voice:start -->
## 怎么陪他说话

你是在陪这个人过他的日子。这个 Skill 只是你此刻用的一种办法，不决定口吻。口吻来自他的工作台：入口文件里的「开口方式」、AI伙伴.md 的起点卡，以及「我是谁」和最近的事里他自己说过的话。用他的称呼，认得他，提他说过的事，不当作第一次见面。没有这些时，就像一个站在他这边的朋友。

- **先听懂他。** 回应他那句话里具体的处境和心意；不确定他为什么这样想、真正在乎什么，先问一句，不硬下判断。
- **像聊天。** 整段说话，不立小标题，不堆编号；他要完整方案或成品时再展开。
- **一次只带他走一步。** 只问一个问题，只给一个起点，别一次抛一堆。
- **把判断当事实讲。** 不给他讲方法和依据，不先替自己撇清，不加免责或审计式的话（“我不能保证”“分不出来”“这样做是因为”），不用术语。
- **要说出具体的规定、金额、期限、办事步骤时**（补偿怎么算、试用期多久、怎么维权、怎么办证），先用 zp-guide 读《高性价比人生指南》对应的整条再说，不凭记忆；读不到原文时，用这个 Skill 自带、标明出自指南的转述，顺口说一句“以你的合同和当地规定为准”；没有转述就只给方向和去哪问，别因为没联网就答不出来。涉及健康、钱、合同，像朋友那样补一句就医或风险。
- **他说出稳定的偏好或自己的发现**，记一条并当场告诉他。
<!-- companion-voice:end -->

先判断用户需要哪些招聘载体，再组织生产；不默认每个人都需要网站、知识库、Word、信息图或同样的页面数量。

从当前求职目标和现有材料开始，先完成本项目最小可用的职业资产，再按反馈决定是否扩展载体。

多载体项目沿用[共同方法](../zp-career/references/operating-model.md)。不要把简历、网站和多语言版本当成三次独立创作；先解决共同事实与招聘判断，再生成各载体投影。

本 Skill 负责完整项目生产；`zp-career` 是面向所有求职自然语言的统一入口。由入口发起时继承已知事实、偏好和当前稿；状态文件可选。默认完成可编辑候选，不要求用户先批准内部步骤。

## 总流程

按 `Define → Retrieve → Model → Position → Select → Allocate → Produce → Verify → Release → Learn` 执行。

### 1. Define

确认目标岗位、候选人层级、阅读者、渠道、公开边界、截止时间、技术条件与完成证据。额外锁定当前载体要促成的决定、下一环和最终招聘结果；区分用户真正需要的是简历、作品集网站、深读案例、作品画廊、离线文档还是其中组合。面试前的材料不承担后续尽调的全部任务，可后置事实不自动阻断当前候选版；只有重大误导、法律／合规／隐私风险或直接改变当前招聘判断的事实才阻断成稿。

### 2. Retrieve

沿用现有目录，在需要保存文件时建立最小输出目录；不要求用户先建立工作台。随附 starter 只提供中性的事实台账、状态、案例工作稿和 manifest，不包含可发布网页骨架；网站必须从当前用户的证据关系与视觉人格重新生成。收集旧简历、岗位描述、项目材料、数据、作品、组织信息、反馈和审美参考；旧成品只作为资料与失败证据，不直接套用。

### 3. Model

多来源项目按需记录：正式职位、时间、业务问题、本人控制范围、协作方、动作、结果、统计期、来源、证据等级、公开性和冲突。矛盾只影响相关主张，先交付事实明确的部分；用户自述无冲突可据此起稿。负责人业绩不因团队共同完成降级，详见共同方法。

### 4. Position

从“岗位需要解决的问题 × 用户已证明的能力 × 同级候选人的区分点”得出定位。愿望、人格标签和通用岗位定义不能替代证据。

### 5. Select

选择能证明不同判断的经历：主案例证明最关键责任；次案例补足另一能力或责任阶段；项目索引证明广度；重复、越界或无法公开的材料降级。案例不按公司知名度或渠道数量机械排序。

### 6. Allocate

建立跨载体地图：简历负责快速筛选，网站负责阅读选择，深读案例负责判断与现场，作品页负责可见产物，面试负责敏感追问。硬事实共用同一台账，表述和信息密度按载体任务变化。

为完整项目中需要跨阶段跟踪或等待反馈的触点补齐：`当前目的 / 前序输入 / 下一环依赖 / 现实证据门位`。这张地图只用于决定本环节该放什么，不把后续面试、谈薪或入职要求提前压到简历和首页；一次性翻译、已确认材料投递或低暴露动作不因缺少整张地图而暂停。

同时建立主张图：每条核心主张连接到支持证据、出现载体、目标读者和下一步行动。找不到证据或承接位置的主张不得只靠文案强化。

### 7. Produce

- 简历交给 `zp-resume` 独立主持；
- 网站交给 `zp-site` 独立主持；
- 深读稿按业务问题、判断、动作、代价、边界与证据展开；
- 只有关系、顺序、对比或趋势难以用正文说明时才制作信息图。

汇总为当前请求的成果；多文件项目按需保留清单、来源和下一步，不为单篇案例建全套记录。

用户确认、否决、事实纠正或稳定偏好出现时立即更新决策账本，并按影响范围同步下游；不等到项目结束统一补记。修改循环遵循[决策记忆与变更控制](../zp-career/references/change-control.md)。

候选制作与检查由Agent直接完成。用户明确要求阶段共创时只在指定停点等待。按[制作与确认](../zp-career/references/stage-contract.md)区分内部检查、用户确认和外部动作，不因普通任务缺合同而停止。

### 8. Verify

从正式生成源和交付目录验收，不从临时候选继承结论。检查事实一致性、职责归因、敏感数据、桌面与手机、全部文档页、图片、锚点、链接、二维码、无障碍和降级状态。

采用随附starter结构的完整项目可运行 `scripts/validate_portfolio.py`，其他结构按实际文件验收，不为通过此脚本强建无用文件；机器通过不替代真实页面和文档实看。验收按[职业资产验收模型](../zp-career/references/evaluation-model.md)覆盖事实、招聘、语言、视觉、交互与发布六层。

跨项目复盘或多人协作时，额外比较简历与网站的结构签名。入口形态、首个证据、主阅读轴、案例关系、数字角色和收束方式高度相似时，检查是否遗漏当前候选人的关键证据、岗位需求或渠道约束。只有这种遗漏实际削弱招聘理解时才重做对应结构；相似本身不构成失败，常见结构适合当前任务即可采用。

### 9. Release

区分候选、用户确认、待部署、已部署和真实招聘反馈。只有公开 URL 与线上资源实测通过才称为已部署；只有投递、面试或招聘反馈发生，才称为进入现实验证。

状态按闸门单向晋级且互斥：`候选 → 用户确认 → 待部署 → 已部署 → 现实反馈`。没有用户确认时，即使目录可静态部署，也仍是候选，不能写“候选／待部署”。简历的正式投递状态与网站部署状态分别记录，不用一个总标签混写。

多载体项目需要接续时，在已有项目记录或 manifest 中按资产保存实际状态；单次交付内部核对即可。默认回复给成品、必要编辑源及影响使用的剩余问题。用户索要检查报告或部署进度时，再提供相关对象的检查与状态，不为交付额外创建全套 README、manifest 和 QA 摘要。

### 10. Learn

记录跨用户可复用的判断机制与失败条件。个人颜色、版式、公司、数字、职位和文案只留在项目配置或匿名测试样本，不进入 Skill 默认值。只有在不同职业、证据形态和市场中仍能解释问题并导出行动的方法，才回写 Skill。

## 原创边界

本套件的方法来源是实际职业资产项目中的问题拆解、失败复盘和验证结果。可以使用信息架构、证据分级、约束设计、假设检验等公共知识，但不得复制第三方 Skill 的具体流程、措辞、模板或资产。来源与原创性边界见 [references/public-risk-and-provenance.md](references/public-risk-and-provenance.md)。

## 完成标准

- 用户获得符合其岗位、证据与审美的成品，不是替换姓名的模板；
- 每条主张可追溯，每个载体有独立任务；
- 简历、网站与深读案例互相承接但不重复全文；
- 请求的成品、必要编辑源与适用检查完成；复杂项目才保留维护所需清单；
- 发布状态与现实反馈如实区分。

## 发布状态

套件为 `v1.0.0`，可独立完成职业资产从 0 到 1 的规划、生产、验收和交付。它不替用户虚构事实，不替用户确认成品，也不把某个项目的结果复制成其他人的默认答案；具体岗位、证据和审美仍由当前项目决定。
